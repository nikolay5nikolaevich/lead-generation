Решения:
- Модель подключается по подписке Claude Pro через `claude -p`, а не по API. Бюджет
  считается в вызовах модели. `Budget` в state.py: `llm_calls`, `llm_calls_limit`,

  `langchain-core` остаётся как зависимость LangGraph.
- Tavily и Hunter — API с бесплатными квотами, считаются в штуках запросов.
  Ключи обоих лежат в `.env`.
- Отступления от SPEC в models.py: `Fact.quote` с `min_length=1`, статус `PENDING`,
  уверенность email — метка `high` / `low_confidence`, а не число.
- Фикстуры: severtrans-logistic.ru → READY, vektor-cargo.ru (SPA без текста) → NO_DATA,
  pekarnya-kolosok.ru (пекарня) → REJECTED.
- eTLD+1 через `tldextract` с `suffix_list_urls=()` (без сети)
  и `include_psl_private_domains=True` (firma.spb.ru — отдельная компания).
- `search` кладёт сырые URL в `domains`, `normalize_domains` заменяет их доменами.
  `limit` режется в `normalize_domains`: в состоянии лежит ровно то, что будет обработано.
- `dispatch` без доменов возвращает `"export"`, иначе граф заканчивался без export
  и в `out.csv` оставались строки прошлого прогона.
- В `OuterState` добавлен `rejected_domains: Annotated[list[str], operator.add]`
  (отступление от SPEC), CLI печатает отсеянные стоп-листом домены.
- Провайдеры и LLM в узлах — фейки на уровне модуля. Переключатель по `--offline`
  делается на этапе 4; сейчас без `--offline` CLI отказывается работать.
- `SqliteSaver` — отдельный пакет `langgraph-checkpoint-sqlite`, понадобится на этапе 6.

Открытые вопросы:

Приёмка:

  beelogistic.ru — все компании ответственного хранения; из сети 25 запросов к сайтам;
  ролевой info@ у трёх (sorozh, dlg, beelogistic), источник — главная страница.
- Повторный запуск → Tavily вернул другую выдачу (4 домена из 5 новые). Домен из кэша
  (beelogistic.ru) — сеть 0, кэш 5. Проверка кэша на 3 доменах: холодный фетч 5.6–6.6 с
  на домен, тёплый 0.8–2.0 с и сеть 0; после удаления файла кэша — снова сеть и 2.6–4.6 с.
- `leadgen run --offline --limit 3` → READY / NO_DATA / REJECTED; `pytest -q` → 16 passed.
Цифры: Tavily — 3 запроса на прогон; Hunter — 1 проверочный запрос (в прогонах не
понадобился: у всех 9 увиденных компаний адрес нашёлся на сайте).

Решения:
- Выдачу Tavily не кэшируем (решение владельца): SPEC §6 не трогаем. Поэтому повторный
  прогон без сети гарантирован только для доменов, уже лежащих в кэше. Выдача Tavily на те же
  запросы заметно меняется от запуска к запуску — это же скажется на resume (этап 6) и eval (этап 8).
- В `pages.text` лежит сырой ответ сайта (HTML, robots.txt), а не текст trafilatura: из HTML
  берутся ссылки на подстраницы и mailto, и повторный прогон не ходит в сеть. Текст
  извлекается при чтении (`trafilatura.extract` в `HttpPageFetcher.fetch`). Валидатор этапа 7
  должен брать текст так же. Неудачные загрузки кэшируются пустой строкой; сброс — удалить
  leadgen.sqlite.
- Подстраницы ищутся по ссылкам главной (`PAGE_KEYWORDS` в http_fetcher.py: слово в пути
  или тексте ссылки), а не угадыванием путей. На 9 реальных сайтах найдены все три вида.
- robots.txt разбирает `protego`: `urllib.robotparser` читает частое «Disallow: /?»
  как «Disallow: /» (dlg.ru ложно получал NO_DATA) и не понимает `*`.
- Переключение `--offline`: CLI подменяет переменные модулей узлов (`search_provider`,
  `page_fetcher`, `email_finders`); по умолчанию там фейки, тесты их не трогают.
- Email: `email_finders` — список по приоритету, следующий спрашивается, только если
  предыдущий пуст. С сайта — mailto со всех страниц + адреса в тексте контактной, уверенность
  `high`. Hunter: `role`, если Hunter считает адрес generic (шире нашего списка, например
  cargo1@); `high` только при verification.status = valid.
- `FakeLLM` для доменов не из фикстур ставит 3 по всем критериям с пометкой «Заглушка»
  и пишет письмо-заглушку. Иначе реальные домены отсекались гейтом score и узел email
  на реальных данных не запускался. Уйдёт на этапе 5.
- Доводка: `/pricing` найден у 3 сайтов из 9 (таблицы тарифов, +14% текста без фактов для
  ICP), `/cases` — ни у одного. Оставлен набор главная + о компании + услуги + контакты.
- `sqlite3.connect(autocommit=True)` не используется: он есть только с Python 3.12,
  а в pyproject `>=3.11`.

Открытые вопросы:
- Адреса вида dom-logist@yandex.ru и trilonm@mail.ru классифицируются как `personal`
  (нет в списке ролевых). Для метрики «ролевой email ≥60%» (этап 8) решить, считать ли
  ящик компании на публичном домене ролевым.
- Ошибка Tavily или Hunter (квота, 429) роняет весь прогон — `retry_policy` и бюджет на этапе 6.

Решения:
- `claude -p` запускается как `claude.exe` напрямую (`find_claude` в client.py): npm ставит

- Промпт идёт через stdin (страницы не влезают в командную строку Windows), свой короткий

  последний элемент, ответ — поле `structured_output`. Модель — `sonnet` (config.LLM_MODEL).
- Ключ кэша LLM — sha256(system prompt + промпт + схема), модель в ключ не входит. В кэш пишется
  только ответ, прошедший `model_validate_json`. Таблица `llm_cache` в том же leadgen.sqlite.
- Счётчик вызовов пока в `ClaudeClient.calls` (и `cache_hits`), а не в `Budget` состояния:

- Скоринг: схема `RubricRatings` с полем на каждый критерий — модель не может пропустить

- ICP нужен модели в подграфе: `icp_text` добавлен в `CompanyState` и передаётся через `Send`.

- Заглушки FakeLLM этапа 4 (балл 3 и письмо для доменов не из фикстур) удалены.
- Без `--offline` флаг `--icp` обязателен. Пример ICP — icp/3pl-spb.txt (ниша как в фикстурах).
- LangSmith: `@traceable(run_type="llm")` на вызове `claude -p`, узлы графа LangGraph трассирует
  сам. В .env.example `LANGSMITH_TRACING=false`, иначе без ключа каждый прогон пишет ошибки.

## Этап 6 — Чекпоинты, retry и бюджет — 2026-09-19

Статус: закрыт. Ветка «лимит подписки исчерпан» от `claude -p` не проверена вживую
(вызвать нельзя), распознаётся по тексту сообщения.
Создано: leadgen/storage/checkpoint.py, leadgen/graph/{retry,log}.py
Изменено: pyproject.toml (langgraph-checkpoint-sqlite), leadgen/{cli,config,state,models}.py,
leadgen/llm/{client,claude,fake}.py, leadgen/graph/{outer,company}.py, все узлы в leadgen/graph/nodes/,
leadgen/providers/{base,fake,hunter,site_emails}.py (поле `external`), tests/test_fakes.py
Приёмка:
- Временное падение в `score` на 3-м вызове, `leadgen run --limit 10 --icp icp/3pl-spb.txt` →
  упал на evralog.ru (1-й и 2-й — sorozh.ru, dlg.ru). Уже запущенные ветки успели закончиться:
  готовы 6 компаний, 3 не начаты.
- Падение убрано, `leadgen run --resume --thread-id 86ebf219` → evralog.ru продолжился со `score`
  (fetch_pages и extract_facts не повторялись), по 6 готовым компаниям в логе ни строки,
  обработаны 3 новых; CSV — 10 строк. Вызовов модели: 5 в первом запуске, 3 во втором, итог 8.
- `--max-llm-calls 3` (offline) → `BUDGET_STOP`, без исключения, CSV: готовые + severtrans-logistic.ru
  со статусом BUDGET_STOP; `--resume` дорабатывает его с `extract_facts`. На реальном клиенте
  `--limit 15 --max-llm-calls 0` → 9 компаний из кэша готовы, 6 — BUDGET_STOP, код выхода 0.
- `leadgen run --offline --limit 3` → READY / NO_DATA / REJECTED; `pytest -q` → 19 passed.
Цифры: offline-прогон — 6 вызовов модели, 3 запроса к поиску, 0 к Hunter.

Решения:
- Остановка по бюджету — исключение `BudgetExhausted`, а не маршрут подграфа в END (отступление
  от SPEC §4). Ветка, дошедшая до END, считается завершённой, и resume её не перезапустит. Незавершённая
  по исключению ветка при `--resume` продолжается с узла, где стояла. CLI ловит исключение, печатает
  BUDGET_STOP с командой продолжения и пишет CSV: готовые лиды + остальные домены со статусом BUDGET_STOP.
- Лимит проверяет общий на все ветки объект LLM (`ClaudeClient`, `FakeLLM`) под блокировкой, а не узел
  по состоянию. Все ветки получают через Send один и тот же снимок состояния и не видят вызовов друг
  друга, так что проверка по состоянию пропустила бы до 3 вызовов на каждую ветку. Состояние хранит
  счёт для чекпоинта и отчёта: `Budget` с reducer `add_budget` в OuterState и CompanyState, узлы
  возвращают прирост.
- `--max-llm-calls` — лимит на запуск процесса: при `--resume` счёт идёт заново. Поле
  `llm_calls_limit` убрано из `Budget`: лимит — параметр запуска, а не данные прогона.
  Итог за прогон (все запуски) — в `budget` состояния, CLI печатает его в конце.
- `llm_calls` считает только настоящие вызовы: ответ из кэша бесплатен. Поэтому методы LLM
  возвращают пару (ответ, число вызовов). `FakeLLM` считает каждый ответ вызовом, чтобы бюджет
  проверялся offline. CLI ставит один объект LLM во все узлы и в offline-режиме.
- `email_lookups` — только запросы к Hunter (`external` у поставщика: True у Hunter с ключом).
- Подграф компилируется без чекпоинтера: вызванный внутри узла, он берёт чекпоинтер внешнего графа
  и сохраняет шаги под именем ветки. Поэтому упавшая ветка продолжается с упавшего узла.
- Чекпоинтер в том же leadgen.sqlite. Сериализатор с явным списком классов из leadgen.models
  (иначе LangGraph предупреждает на каждую загрузку, а в будущих версиях вернёт словари).
  `Fact.source_url` отдаётся в `model_dump()` строкой: `HttpUrl` msgpack не пишет.
- `retry_policy`: сетевые узлы (search, fetch_pages, find_email) — на httpx TransportError, 429 и 5xx;
  узлы с моделью — на `ClaudeError` (сбой вызова) и таймаут. `BudgetExhausted` и ошибки в коде не повторяются.
- `MAX_CONCURRENCY = 4` в config.py. Замечено: после падения одной ветки LangGraph дожидается уже
  запущенных веток и может начать ещё одну, их результаты сохраняются.
- Лог по каждому узлу компании с пометкой «вызов модели» / «ответ из кэша» (leadgen/graph/log.py).
- `--thread-id` без `--resume` для существующего прогона — ошибка: новый прогон поверх старого
  дописал бы лиды к старым через reducer.

Открытые вопросы:
- Текст ошибки лимита подписки взят из бинарника claude.exe («You've hit your limit», «usage limit
  reached»); при первом настоящем исчерпании проверить, что прогон ушёл в BUDGET_STOP.
- В выдаче Tavily попадается yandex.ru (NO_DATA) — кандидат в STOP_DOMAINS.
- В leadgen.sqlite остались чекпоинты проверочных прогонов (в т.ч. 3d37a73b, остановлен по бюджету).
  Их продолжение потратит лимит; удалять не обязательно.

  особенно важна» склеивает две цитаты и добавляет вывод; проверяющая модель это пропустила.
- Подставленное в READY-письмо evralog.ru «у вас 30 складов по всей России и собственная WMS на SAP» →
  verify_draft нашёл оба утверждения (временный скрипт, 2 вызова).
- Валидатор на всех 95 фактах из кэша LLM (11 доменов) → отброшен 1: sklad78.com, модель склеила
  пункты списка без маркеров «•». Ложное срабатывание, допустимое по заданию.
Цифры: проверка письма — 1 вызов, с переписыванием — 3 (проверка, письмо, проверка). Компания,
дошедшая до письма, теперь стоит 4–6 вызовов вместо 3.

Решения:
- validate_facts берёт текст из `state["pages"]`, а не заново из PageCache: это текст, который выдал
  fetch_pages (он сам читает кэш) и который видела модель, с той же обрезкой MAX_CHARS_PER_PAGE.
  Цитата ищется только на странице из `source_url`; страницы нет среди загруженных — факт отброшен.
- Нормализация: casefold, типографские кавычки → прямые, любые пробельные символы (в т. ч. неразрывный)
  → один пробел. Маркеры списков, тире, ё/е не нормализуются.
- verify_draft: модель выписывает утверждения о компании-получателе и номера подтверждающих цитат,
  решает код: утверждение без номера или с несуществующим номером — без опоры. Утверждения о нас
  и нашем предложении не проверяются — они из ICP.
- Модели для сверки даются только цитаты, без `value`: пересказ бывает шире цитаты. На первой версии
  промпта (с value) письмо na-sklad.ru получило READY с «грузами, чувствительными к температуре»,
  которых в цитате нет.
- Переписывание — draft_email с обратной связью: прошлый черновик и список утверждений без опоры.
  Без неё промпт совпал бы с первым, и кэш LLM вернул бы то же письмо. Промпт первого письма
  не изменился посимвольно, старые письма берутся из кэша.
- `unsupported_claims` в CompanyState — и обратная связь для переписывания, и признак «уже переписывали»:
  непустой список при входе в verify_draft значит вторую проверку. Статус READY ставит verify_draft,
  а не draft_email; PENDING после проверки — маршрут на переписывание.
- Письмо со статусом DRAFT_UNVERIFIED остаётся в CSV для ручной правки, утверждения без опоры видны в логе.
- FakeLLM.extract_claims: утверждения — цитаты в «ёлочках» из письма, опора — факт с той же цитатой.
  Проверено временным скриптом: письмо с выдуманной «цитатой» → переписывание → DRAFT_UNVERIFIED или READY.

Открытые вопросы:
- 3 из 5 писем — DRAFT_UNVERIFIED. Основная причина — промпт письма: «чем мы полезны именно им» модель
  понимает как догадки о трудностях компании («при таком масштабе точность учёта особенно важна»),
  и переписывание не всегда их убирает. Доводка промпта письма — этап 8.
- Проверяющая модель пропускает склейку двух цитат с выводом (na-sklad.ru). Замерить долю на golden set.
- В CSV нет колонки с утверждениями без опоры: для DRAFT_UNVERIFIED они только в логе. Нужна ли — решить владельцу.
- Проверка на спамность формулировок (SPEC 5.7) в задание этапа не входила и не сделана.
- Ложные срабатывания валидатора на списках (маркеры «•» в тексте страницы, модель их убирает).

Сверка с SPEC §10:
- Прогон на 50 без ручного вмешательства, в лимите, счётчики известны — выполнен (expo50, цифры выше).

  фактов expo50 временным скриптом — 9/9.
- Падение на середине восстанавливается без повторных вызовов — проверено на этапе 6 (thread 86ebf219); подграф
  компании с тех пор менялся только в промптах и гейте score, в этом этапе падение не повторяли.

Решения:
- ICP сменён по решению владельца: не 3PL, а российские компании, выходящие на международные выставки (Китай, ОАЭ,
  Германия); мы предлагаем участие на наших стендах. icp/expo-export.txt подтверждён владельцем; «кто не подходит»
  и формулировку предложения по его просьбе написал Claude. icp/3pl-spb.txt оставлен примером.
- Флаг ревью лежит в состоянии (`review_domains`): при --resume граф узнаёт о паузе из чекпоинта. Узел отдельный,
  ветвление — маршрутизатор после normalize_domains. При --resume `invoke(None)` перезапускает review_domains, он
  снова встаёт на interrupt(), и CLI показывает список заново. Человек вводит номера доменов, которые убрать.
- Лимит режется до ревью (в normalize_domains): вычеркнул 31 из 50 — обработано 19.
- Поиск: запросов max(3, ceil(limit/10)), по 20 результатов (максимум Tavily) — иначе на --limit 50 было 26 доменов.
  Промпт plan_queries: запрос словами самой компании — продукт и кто она, без признаков потребности и нашего
  предложения (итерации 1–2 журнала).
- Гейт скоринга: при need < NEED_MIN_RATING (2) — REJECTED при любом балле. В широком ICP отрасль и регион ставят 3
  почти любой компании и сами дотягивают до порога; перевес веса need пропускал иностранного экспортёра.
- Промпт письма: о нашем предложении — только сказанное в ICP, без выводов, связывающих его с компанией.
- run_eval.py: домены golden set проходят normalize_domains (стоп-лист) и process_company, без поиска (выдача
  меняется). «Релевантные» = из READY / DRAFT_UNVERIFIED / NO_EMAIL доля с меткой true. Ролевой email считает также
  ящик компании на бесплатной почте, опубликованный на её сайте (решение владельца); адреса от Hunter — нет.
- Golden set: 20 доменов из пробных выдач нового ICP, 4 подходящих, в т. ч. «трудные» отказы — производители без
  признаков экспорта. avzvet.ru и elvpr.ru размечены true при размере больше 300: владелец сказал, что размер не критичен,
  а в ICP стоит 10–300 — гейт size сейчас их не режет (size=0 не отсеивает), но при правке рубрики это всплывёт.

Открытые вопросы:
- Главное: поиск почти не находит целевые компании. В выдаче из 50 доменов подходят 1–2; остальное — СМИ, каталоги,
  посредники, производители без экспорта. Скоринг отсеивает их верно, поэтому доля релевантных высокая, а лидов
  единицы. Универсальный веб-поиск не ищет по признаку «экспортирует / ездит на выставки». Кандидат на следующий шаг —
  списки участников выставок (российские павильоны) как источник доменов. Вторая идея — организаторы как отдельный ICP
  (нужен ответ владельца, что им предлагать; зарубежным нужны письма на английском).

  consultant.ru, cyberleninka.ru, productcenter.ru, fabricators.ru, manufacturers.ru, oborudunion.ru и др.).
