# Агент лидогенерации на LangGraph — спецификация MVP

## 1. Зачем этот проект

Работающий CLI-инструмент, который экономит менеджеру часы ручного поиска компаний
и переписывания одного и того же письма.

Внешние сервисы прячутся за узкими интерфейсами и подменяются заглушками:
так граф можно гонять целиком без сети, а сервис заменить, не трогая граф.

## 2. Пользователь и сценарий

B2B-стартап или агентство. Менеджер описывает идеального клиента обычным текстом,
запускает скрипт, через несколько минут получает CSV с готовыми к отправке лидами.
Решение об отправке остаётся за человеком — MVP ничего не рассылает.

## 3. Вход и выход

**Вход:** текст ICP (отрасль, размер, регион, признаки потребности), лимит компаний
за запуск, опциональные флаги (`--offline`, `--review-domains`, `--max-llm-calls`).

**Выход:** CSV, одна строка на компанию: название, домен, краткое описание,
извлечённые факты с URL и цитатой источника, балл соответствия с разбивкой по критериям
и обоснованием, email с типом и уверенностью, черновик письма, статус обработки.

## 4. Архитектура графа

Центральное решение проекта — **два уровня состояния**, потому что параллельные ветви
не могут писать в один и тот же ключ состояния.

### OuterState

```python
class OuterState(TypedDict):
    icp_text: str
    limit: int
    queries: list[str]
    domains: list[str]
    leads: Annotated[list[Lead], operator.add]   # reducer складывает результаты ветвей
    budget: Budget                               # счётчики вызовов модели и внешних запросов
```

### CompanyState

Изолированное состояние одной компании внутри подграфа: домен, загруженные страницы,
факты, оценка, email, письмо, статус. Ветви друг о друге не знают.

### Топология

```
ICP → plan_queries → search → normalize_domains → [interrupt?] → dispatch
                                                                    │ Send(...)
                                        ┌───────────────────────────┴────────┐
                                        ▼            ▼              ▼        ▼
                                   company_subgraph (по одной ветви на домен)
                                        └───────────────────────────┬────────┘
                                                                    ▼
                                                                 export
```

`dispatch` возвращает `[Send("company_subgraph", {"domain": d}) for d in domains]` —
это и есть map-reduce в LangGraph.

### Подграф компании

```
fetch_pages → extract_facts → validate_facts → score → [gate] → find_email → draft_email → verify_draft
```

Условные переходы:

- нет текстового контента → статус `NO_DATA`, ветвь завершается;
- балл ниже порога → статус `REJECTED`, письмо и email не ищем;
- email не найден → статус `NO_EMAIL`, лид всё равно сохраняется;
- бюджет исчерпан → статус `BUDGET_STOP`.

Статусы — `enum`, не строки.

## 5. Функциональные блоки

### 5.1 Поиск компаний

ICP → несколько поисковых запросов (structured output, не свободный текст). Сбор доменов,
нормализация (`www`, схема, trailing slash), дедупликация по eTLD+1, отсев по стоп-листу:
агрегаторы, каталоги, соцсети, медиа, маркетплейсы.

### 5.2 Сбор информации

`httpx` + `trafilatura`: главная, about, продукт/услуги, контакты. Обрезка текста до
разумного объёма с сохранением URL каждого фрагмента. Уважение `robots.txt`,
честный User-Agent, никаких обходов блокировок. Playwright — только если реально
упрёшься в JS-сайты, и тогда как отдельная реализация того же интерфейса.

### 5.3 Извлечение фактов

Structured output. Каждый факт — отдельный объект:

```python
class Fact(BaseModel):
    kind: FactKind        # enum: what_they_do, size, industry, clients, hook, ...
    value: str
    source_url: HttpUrl
    quote: str            # дословная цитата со страницы
```

### 5.4 Валидация фактов (машинная, а не декларативная)

`validate_facts` проверяет, что `quote` действительно является подстрокой закэшированного
текста страницы после нормализации пробелов. Не прошло — факт отбрасывается и логируется.
Это превращает правило «только факты со ссылкой на источник» в автоматический тест.

### 5.5 Скоринг

Фиксированная рубрика из 4–5 критериев. По каждому модель выдаёт **enum-оценку 0–3
и текстовое обоснование**. Итоговый балл 0–100 считает Python взвешенной суммой —
модель не просят калибровать «73 или 78», потому что она этого не умеет.
Ниже порога компания дальше не идёт.

### 5.6 Поиск email

По приоритету:

1. ролевые и корпоративные адреса, найденные прямо на сайте (`info@`, `sales@`, контактная страница);
2. один внешний провайдер (Hunter.io) за интерфейсом `EmailFinder`.

Для каждого адреса хранится источник, тип (`role` / `personal`) и уверенность.
Неподтверждённые помечаются `low_confidence` и никогда не выдаются за проверенные.
Приоритет ролевых адресов — не только техническое решение, но и требование по
персональным данным.

### 5.7 Черновик письма

Короткое письмо строго на фактах из состояния. Затем `verify_draft`: второй проход
вытаскивает утверждения из черновика и сверяет каждое с `fact_id`. Утверждение без
опоры на факт — письмо переписывается один раз, при повторной неудаче статус
`DRAFT_UNVERIFIED`. Отдельно — проверка на спамность формулировок.

### 5.8 Экспорт

CSV. Google Sheets в MVP не входит.

## 6. Инфраструктура

**Один SQLite-файл, три таблицы** — это три разных уровня, и их легко перепутать:

| Уровень | Что делает |
|---|---|
| Чекпоинтер (`SqliteSaver`, `thread_id` = запуск) | восстанавливает позицию в графе после падения |
| Кэш страниц (`url → text, fetched_at`) | не качать сайт заново при смене промпта |
| Кэш LLM (`hash(промпт + схема) → ответ`, своя таблица) | не тратить лимит подписки на идентичный промпт |

**Модель — по подписке Claude Pro, не по API.** Вызов идёт через CLI Claude Code:
`claude -p` запускается отдельным процессом, структурированный ответ задаётся флагом
`--json-schema` (схема берётся из Pydantic-модели через `model_json_schema()`),
результат проверяется `model_validate_json()`. Следствия:

- расход меряется не в долларах, а в числе вызовов модели: у подписки нет счёта,
  есть лимиты использования за окно времени;
- `with_structured_output` и `set_llm_cache` из LangChain недоступны — их роль
  выполняют `--json-schema` + Pydantic и своя таблица кэша;
- число одновременных веток ограничивается (`max_concurrency` в конфиге запуска
  графа), иначе параллельные вызовы быстро выбирают лимит подписки;
- исчерпание лимита подписки — штатная ситуация: ветка получает `BUDGET_STOP`,
  а прогон продолжается позже через resume из чекпоинта.

**`retry_policy`** на всех сетевых нодах — встроено в LangGraph, трогаем руками.

**Offline-режим** (`--offline`): сохранённые HTML-фикстуры плюс фейковый LLM. Граф
гоняется целиком без сети и без расхода лимитов. Делается в первый день и экономит все последующие.

**Бюджетный предохранитель:** счётчики вызовов модели, поисковых запросов и запросов
к Hunter в состоянии; нода проверяет лимит вызовов модели (`--max-llm-calls`)
и останавливает граф. Квоты Tavily и Hunter тоже считаются в штуках запросов.

**Human-in-the-loop:** одна точка `interrupt()` после сбора доменов (`--review-domains`) —
человек вычищает мусор из списка, граф продолжается через `Command(resume=...)`.
Минута человеческого времени в самом полезном месте.

**Наблюдаемость:** LangSmith для трассировки. Golden set из 15–20 размеченных руками
компаний для измеримой проверки качества.

## 7. Технологии

LangGraph (оркестрация), Claude Pro через CLI `claude -p` (модель, structured output
через `--json-schema`), Pydantic (схемы),
Tavily или Exa (поиск), `httpx` + `trafilatura` (парсинг), Hunter.io (email),
SQLite (чекпоинты и кэш), LangSmith (трассировка), Typer или argparse (CLI).

## 8. Границы MVP

Не входит: отправка писем, цепочки фоллоу-апов, обработка ответов, интеграция с CRM,
веб-интерфейс, Google Sheets, второй провайдер email, парсинг соцсетей и LinkedIn,
новостной поиск «свежих событий» (только то, что есть на сайте).

## 9. Риски

| Риск | Что против него |
|---|---|
| Мусор в выдаче вместо реальных компаний | стоп-лист доменов, нормализация, `interrupt` на ревью |
| Сайты без текстового контента | статус `NO_DATA`, ветвь не ломает пачку |
| Выдуманные факты в письмах | quote-валидация фактов + `verify_draft` |
| Исчерпание лимита подписки посреди прогона | лимит вызовов модели, `max_concurrency`, три уровня кэша, offline-режим, resume из чекпоинта |
| Персональные данные | приоритет ролевых адресов, источник каждого адреса, никакой рассылки |
| Хрупкость внешних API | интерфейсы с подменой, `retry_policy` |

## 10. Критерии готовности

- Прогон на 50 компаниях проходит без ручного вмешательства, в рамках заданного лимита
  вызовов модели, и число вызовов модели и внешних запросов за прогон известно явно.
- ≥70% найденных доменов — реальные компании, соответствующие ICP; **проверяется на golden set**,
  а не на глаз.
- Ролевой или корпоративный email найден для ≥60% лидов. Персональный адрес — бонус, не критерий.
- 100% фактов в письмах проходят quote-валидатор (жёсткий автоматический гейт).
- Падение на середине пачки восстанавливается из чекпоинта без повторных вызовов модели
  по уже сделанной работе — проверяется специально устроенным падением.

## 11. Порядок реализации

Проект разбит на **8 этапов**, каждый даёт запускаемый результат. Этапы 1–3 сделаны.
Задания на этапы 4–8 лежат в `stages/stage-NN.md`, запуск — командой `/stage N`.
Ход работы фиксируется в `PROGRESS.md`: он заменяет память между сессиями.

| № | Этап | Критерий приёмки |
|---|---|---|
| 1 | Каркас, схемы, фейковые провайдеры | `pytest -q` проходит, схемы валидируются |
| 2 | Внешний граф: `Send`, reducer, fan-out | `leadgen run --offline --limit 3` создаёт CSV с 3 строками |
| 3 | Подграф компании и условные переходы | три фикстуры дают три разных статуса |
| 4 | [Реальные источники: поиск, фетчер, email, кэш](stages/stage-04.md) | реальные домены и ролевой email; повторный прогон без сети |
| 5 | [Реальный LLM: факты, скоринг, письмо](stages/stage-05.md) | полный прогон на 5 компаниях |
| 6 | [Чекпоинты, `retry_policy`, бюджет](stages/stage-06.md) | падение на 3-й из 10, затем resume без переобработки |
| 7 | [Гейты качества: валидация фактов и письма](stages/stage-07.md) | выдуманный факт отбрасывается автоматически |
| 8 | [`interrupt()`, golden set, прогон на 50](stages/stage-08.md) | критерии раздела 10 проверены по пунктам |
